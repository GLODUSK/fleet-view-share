# Fleet View

A live view of every Claude Code session on this machine, in its own app window (or, with `--tui`, in the terminal): what each one is doing right now, its running agents, how far its current plan has got, and how close its work is to production. Four views: **Cards** (one card per conversation), **Map** (a graph of conversations, agents, repos, PRs and shared files, like Obsidian's graph view), **Wall** (one big tile per conversation, for a second monitor) and **Projects** (Claude Code's own layout: each repo with its conversations under it, and the picked one as a chat). Each conversation also shows its tokens and what they would cost at API prices.

## Install on your own PC

Windows 10/11 with [Node.js 18+](https://nodejs.org) (`winget install OpenJS.NodeJS.LTS`), git (`winget install Git.Git`) and [Claude Code](https://docs.claude.com/en/docs/claude-code) logged in with your own Claude account. To install Claude Code, in PowerShell: `irm https://claude.ai/install.ps1 | iex`, then run `claude` once and log in.

Then clone Fleet View into your home folder and run its installer. In PowerShell:

```
git clone https://github.com/GLODUSK/fleet-view-share.git "$HOME\fleet-view"; powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\fleet-view\install.ps1"
```

Or in Command Prompt:

```
git clone https://github.com/GLODUSK/fleet-view-share.git "%USERPROFILE%\fleet-view" && powershell -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%\fleet-view\install.ps1"
```

`install.ps1` checks what it needs, installs the desktop window (`desktop/`, Electron, with `npm ci`), puts the folder on your user PATH (so `fleet-view` and `fv` work in any new console), installs the `fleet-view` skill and the `fleet-view-feed` mod (below) into every Claude login (`~/.claude` and each `~/.claude-<letter>`), and starts Fleet View. Add `-StartAtSignIn` to start it at sign-in, `-NoDesktop` to use an Edge app window instead, `-NoLaunch` to not start it. It needs no admin rights and sends nothing anywhere: it reads your own `~/.claude` and serves its page on `127.0.0.1` only, to this machine's own browser window; the scripting API needs a token made on first start (`%LOCALAPPDATA%\fleet-view\api-token`). It ends by saying which version it installed (below: **Versions**). A login you add later (a second account) gets the skill and the mod when you run `install.ps1` again.

**To update**, use **Update now** in Fleet View (below: **Update available**), or run the same `install.ps1` again (the `powershell … install.ps1` part above), also while Fleet View runs: it pulls, then puts the update in. The server and the page reload by themselves; a changed session host (`desktop/host.js`, `handoff.js`) restarts once no session is mid-turn and resumes them; any other change in `desktop/` restarts the window (the sessions keep running). When the update changes the desktop window's packages, `npm ci` can't run under a running window, so it asks **Quit Fleet View now? [y/N]** first: yes closes the window, saves the open sessions, ends them and quits, and Fleet View starts again at the end with every session resumed; no (or a run with no console to ask in) stops with: choose **Quit everything** from the tray icon, then run it again. A `desktop\package-lock.json` changed by hand (`npm install` does that) is put back as committed first.

It works with one Claude account (`~/.claude`); every other login in a `~/.claude-<letter>` folder (`~/.claude-a` is A, `~/.claude-c` is C, and so on) is another account, with its letter tag, "New session · <letter>" and "Send to Claude <letter>". A new folder shows up within a minute, with no code change. **Send to Claude <letter>** needs the `/handoff` and `/pickup` commands in that login (a skill or a command file; Fleet View doesn't ship them) and the conversation's log in its `projects` folder (one login's `projects` linked to the other's); the menu offers it only for the logins that have both.

For the maintainer: the share repo is published from the main repo with `node scripts/publish-share.js` (below: **Update available**).

## Run

Type `fleet-view` in any cmd window. The folder is on the user PATH, so the command works from anywhere.

**The app window is the default.** `fleet-view` starts a small server on `http://127.0.0.1:4777` (this machine only) and opens it in the app window: the blurred desktop window when it is installed (below), otherwise a Microsoft Edge app window (no tabs, no address bar, its own Edge profile under `%LOCALAPPDATA%\fleet-view\edge`). The window opens where it was last time and saves its place and size. No console window shows: `fleet-view` hands off to `fleet-view.vbs`, which runs the launcher hidden, and the desktop app runs the server hidden and stops it when it quits. Run (Win+R) and the Start menu's search go straight to `fleet-view.vbs` too: the server registers the name `fleet-view` in App Paths and adds a **Fleet View** Start menu shortcut (with its icon, to pin) when one is missing, so no Windows Terminal window flashes up. Typed in a terminal, `fleet-view` still runs `fleet-view.cmd` there. Typing `fleet-view` again while it runs just brings up the window on the same server (Edge opens another one). When `node` isn't on the PATH `fleet-view.vbs` was started with, it says so in a message box ("Fleet View needs Node.js 18 or newer, and node was not found.") instead of failing with nothing on screen.

### Desktop window (blurred, like the Windows Terminal tabs)

`desktop/` holds a small Electron shell that shows the same page in a window with Windows 11 acrylic behind it: the desktop and the windows behind it show through, blurred, like the Fleet View terminal profile. Edge app windows can't be see-through, which is why this exists. `install.ps1` installs it (`npm ci` in `desktop/`, from the committed `package-lock.json`); don't run `npm install` there, which can rewrite that file and then blocks **Update now**.

From then on `fleet-view` opens this window instead of Edge. It picks Electron whenever `desktop/node_modules/electron` is there and falls back to Edge when it isn't (delete `desktop/node_modules` to go back to Edge).

- The page loads with `?glass=1` and switches to glass mode: the background, cards, panels, header and footer are tinted see-through instead of solid, and the map canvas is left clear; text keeps its full colour. Menus, the confirm box, toasts and the map's tooltip and legend are frosted with a strong tint, so nothing behind them shows through. In Edge or a browser the surfaces are solid.
- The window has no title bar of its own: the header is the title bar. Drag it to move the window and double-click it to maximize; the minimize, maximize and close buttons sit over its right end. The tabs, the repo menu and the filter take clicks as usual, and the header pills show their tooltips. When the window is too narrow for one row, the header drops parts in turn (the pill labels, which stay in their tooltips, then "Fleet View", the clock, the pills) and never cuts any. A window started by an older `main.js` keeps its frame and the usual header until it restarts.
- One window per port: starting Fleet View again brings the open window to the front instead of opening a second one (the reload after an update passes `--no-open` anyway). Its profile lives in `%LOCALAPPDATA%\fleet-view\electron-<port>`.
- The window saves its own place and size: in its profile folder (`window-state.json`, which it reads first, with whether it was maximized) and on the server (`webBounds`, the same setting the Edge window used, so it first opens where the Edge window was). It is put back with the same restored (not maximized) bounds it saved, once when it is made and again just before it shows, and moves while it is being placed are not saved. If that place is on no screen any more, it opens in the middle of the main display.
- **Mini view.** `m`, or the small square button at the right end of the header, shrinks Fleet View into a small glass window that stays on top of other windows and has no taskbar button: the main window hides while it shows. It has the live and waiting counts, the clock, and up to three sections: **Needs you** (asking, a question, an API error, stalled; most urgent and longest waiting first, with what it asks), **Working** (every conversation at work, newest action first, with a progress ring, its repo, running agents and its last action) and **Just finished** (the last hour's, up to 3, with how far each shipped). Its height follows its rows (up to 8, then it scrolls). Its expand button or `Esc` brings the main window back as it was (same place and size, maximized or not); a click on a row does the same with that conversation picked and its panel open. Drag its top bar to move it. It remembers its place (`miniBounds`) and comes back on a screen if its old place is on none; the app always starts on the main window.
- **Tray icon.** An orange diamond in the notification area: click it to bring up the window; its menu has **Show Fleet View**, **Mini view** (a checkbox), **Close window (sessions keep running)** and **Quit everything** (see "Live sessions in the panel"). Its tooltip gives the live and waiting counts and the sessions running here. Closing the main window quits the app, mini view and tray included, and the server the app started with it; the sessions keep running in the session host.
- It only ever shows the local page. Links (PRs, branches, deploys) open in the default browser, https only; anything else is refused. The page has no Node access (sandboxed, context isolation on).
- The blur stays when the window isn't focused, like Windows Terminal's "acrylic when unfocused". Windows 11 turns acrylic off for inactive windows (flat grey), so each time the window loses focus a small hidden PowerShell helper (`desktop/backdrop.js`, started with the window and closed with it) sends it `WM_NCACTIVATE`, which keeps the backdrop on. The side effect: the title bar stays drawn as active while another window has focus. Focus and typing are unchanged.
- `F5` / `Ctrl+Shift+R` reload (plain `Ctrl+R` is the chat box's history search), `F12` / `Ctrl+Shift+I` dev tools.
- Before Windows 11 22H2 there is no acrylic; the window shows the page's dark tint over a plain background.

```
fleet-view                      app window (same as node fleet-view.js --web)
fleet-view --tui                the terminal view, exactly as before
fleet-view --port 4800          serve on another port
node fleet-view.js --web --no-open --demo   serve made-up data without opening a window
```

### Terminal view (`--tui`)

Once, add the blurred Windows Terminal profile (in the Fleet View folder):

```
node fleet-view.js --install-profile
```

Then run `fleet-view --tui`. Outside Windows Terminal it opens its own window with the "Fleet View" profile (acrylic blur, 45% opacity). Inside Windows Terminal it runs in the current tab. The profile runs `fleet-view.cmd --tui`; run `--install-profile` again if yours was added before the app window existed (it would open the app window instead). The view never paints a background colour, so whatever blur the tab has shows through; `--solid` paints one instead.

**Updates reload in place.** When `fleet-view.js` (or `api.js`, which it loads) changes on disk (a pull or merge), Fleet View reloads itself: `fleet-view.cmd` runs it in a small loop that starts it again when it exits with code 75. In the app window the server restarts with `--no-open`, so no second window appears; the page shows a small "reconnecting" note and picks up the new server by itself. In the terminal it reloads in the same tab, so the window keeps its place and size. A version that doesn't parse is ignored until it does. When the page's own files (`web/`) change, the page reloads itself a few seconds later, in the same window. Run `--install-profile` once more after updating from an older version, so the profile goes through `fleet-view.cmd`.

**Versions.** Every copy of Fleet View has a version number, MAJOR.MINOR.PATCH (`1.0.12`), the same number for the same code on every PC, so "which version are you on" has a plain answer. `version.json` at the repo root holds MAJOR.MINOR (`"1.0"`); PATCH counts the commits on `main` (first parent) since that file last changed, so every merged PR moves it up by one (`version.js` works it out with git). Edit the number in `version.json` for a bigger step (`1.1`, `2.0`) and PATCH starts again at 0. The share repo's copy of `version.json` already holds the full number and the main commit it came from (`{ "version": "1.0.12", "commit": "<sha>", "published": "<date>" }`, written by `publish-share.js`), so a friend's PC knows its version without main's history; each publish is also tagged `v1.0.12` there. To see it: the small **v1.0.12** at the right end of the footer (a click opens the update card: **Fleet View 1.0.12 · up to date**, Check again, the automatic-update switch), `fleet-view --version`, `fv version`, `node version.js`, `GET /update`'s `version` and `GET /api`'s `fleetView`. `server.log`'s start line says `version 1.0.12 (02dddec)`: the number, then the commit. Without `version.json` (or git, on main) every one of these falls back to the short commit.

**Update available.** Fleet View checks its folder's git upstream a minute after it starts and every 30 minutes after that (`updater.js`). When there is something new, an **Update available · N** pill shows in the header (and the footer's version turns green); a click opens a card with the versions (**1.0.10 → 1.0.12**), what changed (the commit messages; for the share repo, the notes `publish-share.js` wrote), **Update now**, **Check again** and an **Update automatically when no conversation is working** switch (kept in `%LOCALAPPDATA%\fleet-view\update.json`). Update now runs `git pull --ff-only`, then the server and page reload themselves; a change in `desktop/` restarts the window (the sessions live in the host and stay), and a changed `host.js` or `handoff.js` runs `desktop\restart-host.js`, which waits until no session is mid-turn. After the pull it copies the new `fleet-view` skill into every Claude login whose copy differs. The card's notes leave out each share commit's "Fleet View 1.0.12" title (the card shows the versions) and the dash in front of each line. It refuses when files in the folder were changed locally (a `desktop\package-lock.json` that `npm install` rewrote only when the update changes it too; the card then gives the `git checkout` that puts it back), and, where the desktop window is installed, when `desktop/`'s packages changed: then the card gives the `install.ps1` command to run, which asks to quit Fleet View first (see **To update** above). With the Edge window (`-NoDesktop`) those packages don't matter and the update goes in as usual. Routes: `GET /update`, `POST /update/check`, `POST /update/apply`, `POST /update/auto {on}`. After an update the header shows **Updated to 1.0.12** for a while. Publishing: `node scripts/publish-share.js --notes "what changed"`, or without `--notes` it lists the titles of the PRs merged since the last publish; the share commit is titled `Fleet View 1.0.12`, and the script prints `published: 1.0.12 (<main commit>) on GLODUSK/fleet-view-share`, or `the share repo already has this version` when there is nothing new to publish (also when main's new commits change only files the share repo leaves out, such as `CLAUDE.md`). `--dry-run` prints the version and the file list and publishes nothing.

**Crashes restart by themselves.** If the server hits an error nothing catches, it writes the error and its stack to the log (below) and exits with code 76. `fleet-view.cmd` then starts it again after 3 seconds, with `--no-open`, so the open window just reconnects. Any other non-zero exit counts as a crash too. After 5 crashes within 2 minutes it stops trying and says so in the log; type `fleet-view` to start it again. Exit code 0 (Ctrl+C, closing the console, or another Fleet View already serving the port) ends the loop as before. One unreadable line in a session log is skipped and logged, never fatal, and a request that fails gets a `500` instead of stopping the server.

**Log.** The server writes a small log to `%LOCALAPPDATA%\fleet-view\server.log`: a line when it starts (pid, version as the number and the git commit, `1.0.12 (02dddec)`, plus `fleet-view.js`'s time, port, and why it restarted, if it did) and when it stops (exit code and reason), every crash and unhandled promise rejection with its stack, HTTP server errors, and the launcher's restart and give-up lines (`[fleet-view.cmd]`). Nothing is logged per request, and an error that repeats every poll is written once a minute at most. At 2 MB the log moves to `server.log.1`, replacing the older one.

### Start at sign-in

```
fleet-view --install-startup    make "Fleet View.lnk" in your Startup folder
fleet-view --remove-startup     delete it
```

The shortcut runs `fleet-view.vbs` (no console window), in this folder, so Fleet View starts (and opens its window) when you sign in. Both commands say what they did and run in the console you type them in. The Startup folder is the one Windows reports for your account (`shell:startup`). `/state` reports whether the shortcut is there as `settings.autostart`.

Needs Node 18+ and no packages. The `gh` CLI, logged in, powers the ship track and merge counts.

## Keys

In the app window: `v` or `Tab` next view (Cards, Map, Wall, Projects), click the name top left for the repo menu, `/` filter, arrows pick, `Enter` or `o` (or a double-click) opens the picked conversation, `c` compact cards, `s` steady or live order, `m` the mini view (desktop window only), and in the Map the wheel zooms at the cursor, drag pans, `+` / `-` zoom, `0` recenters, `l` shows the legend. Map repos stay where they are: each keeps the spot it first got (new repos take the nearest free spot, nothing else moves). Drag a repo's hub to move it with everything on it; that pins it, so it never moves by itself again. `g` re-arranges the repos that aren't pinned, `G` unpins all of them too. Spots and pins are saved (`mapSpots` in `~/.fleet-view.json`). The view fits the map when it opens (and on `0`), then holds still: changes never pan or zoom it by themselves. A right-click on a repo or a conversation opens its menu (see "Right-click menus"). In the desktop window that opens its live session in the panel (see "Live sessions in the panel"); in Edge it opens a Windows Terminal tab, and a conversation that hasn't finished asks first, since it may still be open in another window. The footer lists the keys.

**Steady order** (the default; `s` switches to live order and back, and it is saved as `steady`). Cards and Wall put the conversations that need you first (asking, then a question, an API error, stalled), longest waiting first within each. Every other conversation keeps the place it had when the page first saw it, and new ones join at the end, so cards don't swap places each time one of them does something; a card moves only when it starts or stops needing you. Live order sorts by state, then by latest activity, as before. The first-seen order lives in the page only, so it starts over when the page reloads.

**Detail panel.** Picking a conversation (a click in Cards, Wall or Map, the arrows, or a row of the "recently finished" strip) opens a panel on the right: its name, account and state; repo, branch, worktree, model, context and turn time; an **Open in terminal** button; its last reply in full (or the question it waits on); its plan and agents; its ship track with the PR and checks; the files it touched; its last 30 tool calls; and its tokens and cost. It updates every second and keeps its scroll position. On a window wider than 1300 px the view narrows to make room; on a narrower one the panel sits over it. `Esc` or `×` closes it. `Esc` closes one thing at a time, innermost first: the right-click menu, the confirm box, the repo menu, the filter box while you type, Since you looked, the map legend, a selection of several conversations, the panel, then the pick (and an applied filter).

**Chat tab.** The panel opens on **Chat**: the conversation as a chat, read from its log (`GET /conversation`, below), with a real chat box under it that types into the same live session the Session tab runs. Your messages are glass bubbles on the right; Claude's replies run full width as Markdown (marked 18, then DOMPurify 3, so nothing in a reply runs as HTML; links open in the browser), and fenced code is a card with its language and a **Copy** button, coloured by highlight.js 11 (12 languages). Each tool call is one folded row (`Bash · npm test`, `Edit · app.js +4 −2`) that opens to its command and output, a red/green diff for edits, a checklist for todos, the question and options for AskUserQuestion. Select text in the chat and **Reply** quotes it into the box. Scrolled up past your last message, a bar pinned at the top shows it (**You** · its first line); click it to jump back to it. The box is a normal text box (click, select, right-click for Cut/Copy/Paste): `Enter` sends, `Shift+Enter` is a new line, and the draft is kept per conversation. Paste, drop or attach (📎) images: each is saved by `POST /chat/image` and its path goes in the message, which Claude Code attaches as `[Image #N]`. Sending into a conversation that isn't running here starts it (like an explicit open) and waits until Claude is idle. The box reads the live screen too: while Claude works, an activity line shows its spinner text with **Interrupt** (Esc in an empty box does the same; Send only ever sends). What you send shows in the chat at once, marked *Sending* or, while Claude is mid-turn, *Queued*, until the log has it; a queued one has **Unsend** (it leaves Claude Code's queue the way the terminal does it: ↑ pulls the queue into the prompt, `Ctrl+U` clears it, the others are queued again; the queue is read from the log's `queue-operation` lines) and **Interrupt**; a long message (over 400 characters or 6 lines) folds to a few lines behind **Show more · N lines**; hovering one of your messages shows **Rewind**, which runs `/rewind` back to just before it (a session not running here is started first, and one mid-turn is stopped first with Esc, waiting until it is idle; Claude Code then asks what to restore, as a card), after which the chat drops what came after (a prompt whose parent is older than an earlier prompt marks the rewind in the log) and the message comes back into the box to edit; messages typed mid-turn are logged as `queued_command` attachments, and the chat shows those as your messages too; a permission prompt, AskUserQuestion or plan approval shows as a card of buttons (or keys 1–9) that press that option, and nothing is pasted or Entered while one is up; the **Mode** picker presses Shift+Tab until the footer shows Default, Accept edits, Plan or Bypass (never while a question is up). **Slash commands**: type `/` and a list of commands shows above the box (Claude Code's built-in ones, the bundled skills, and the commands and skills in `~/.claude` and the conversation's folder and repo, from `GET /chat/commands`); arrows move, `Tab` puts the name in the box for its arguments, `Enter` runs it, `Esc` closes the list. Any command still works typed in full. What a command prints (`Set model to …`) shows in the chat under it. The **model** pill by Send shows the model and effort the session runs (the effort from the footer under the prompt, else from the last reply) and picks either one: it sends `/model <id>` (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, the 1M-context Opus and Sonnet, each named with its version; the current one is highlighted) or `/effort <low|medium|high|xhigh|max>` into the session, which Claude Code also saves as the default for new sessions. Vendored in `web/vendor/marked`, `highlight`, `dompurify` with their licences. In Edge the chat shows, but sending needs the desktop window.

**Live sessions (desktop window).** Besides Chat, the panel has **Session** and **Details** (everything above). Session runs the conversation itself, the real interactive Claude Code session your terminal shows (`claude --resume <id>`, never headless), in the panel, live, and you type into it there. A click on a conversation starts it there by itself, as a preview that ends when you move on unless you type into it; `Enter` or a double-click starts one that stays; arrow keys only show it; a conversation another window has open is not started, and the tab offers **Open here anyway** (see "Live sessions in the panel" below). It starts in the conversation's last folder (`cwd`), under its account. The session lives in the session host (see "Live sessions in the panel"), so it keeps running while you look at other conversations, when the page or server reloads, and when the window closes; coming back to it replays its screen. While the terminal has the keyboard, every key goes to Claude: no shortcut fires, `Esc` reaches Claude, and the footer says so (click outside the terminal for the shortcuts again). `Ctrl+C` copies when text is selected (otherwise it goes to Claude), `Ctrl+V` pastes, `Shift+Enter` starts a new line. **Reply to a line:** select text in the terminal (drag, double-click a word, triple-click a line) and a small **Reply** button shows by the mouse; it puts the selection in Claude's prompt as `> ` quote lines, with Claude Code's `●`/`⎿` marks and the indent removed, and leaves the cursor on a new line under it for your answer. Nothing is sent until you press Enter. The scrollbar is a thin rounded thumb with no track or arrows; it fades out when idle and widens and turns cyan under the mouse. **⤢ wider** widens the panel to 60% of the window while Session shows, and is remembered. When the session ends, a bar says so with its exit code, with **Reopen** and **Close**. Every conversation opens its panel on Chat, or on the tab you last left it on (kept per conversation in the window). The open panel itself is kept too: close the window (or the page reloads after an update) and it opens again on the same conversation, with the same split chats, tab, place, size and, floating, the spot you last dragged it to. Cards and the map mark it with a small terminal sign ("here"). Closing the window leaves sessions running; tray **Quit everything** asks what happens to them: **Move to Terminal tabs** reopens each one as a tab of one new Windows Terminal window (**Move to console windows** on a PC without Windows Terminal: a console window each), and **Close them** ends them so the next start resumes them. The cursor never blinks. In Edge the Session tab says live sessions need the desktop window and offers **Open in terminal** instead. The terminal is xterm.js 6.0 with its fit addon 0.11, vendored in `web/vendor/xterm/` (MIT, licence files beside them).

**Links.** Wherever they show (cards, wall tiles, the panel, the map), a PR or its checks open on GitHub, a finished `live` step opens the deploy, a branch name opens the branch on GitHub, a repo chip opens the folder in Explorer, and a file opens in VS Code. Links underline under the pointer, and clicking one never picks the card under it. In the Map, a click picks a node and a double-click (or `Enter`, or a second click on the picked node) acts on it.

**Projects view.** The fourth tab works like Claude Code's sidebar. On the left, every listed repo (in the repo menu's order, folded or open by its chevron, remembered) with its conversations under it: the live ones first, then the recently finished, each with its status icon, account and how long ago it last did something; **Older conversations** lists the repo's history (`GET /repo-history`), and **+** opens the repo's menu (New session · A / B and the rest). On the right, the picked conversation as a chat, the same chat and chat box as the panel's Chat tab, under a header with its name, state, repo, branch and goal, and **Session**, **Details** (the side panel on that tab) and **Terminal** buttons. The side panel stays shut in this view otherwise. `↑↓` (or `j`/`k`) move through the list, `Enter` (or a double-click) puts the cursor in the chat box, and a right-click on a repo or conversation opens its menu. The pick carries over from and to the other views and is remembered in the window. The terminal view (`--tui`) has no Projects view and shows Cards instead.

**Recently finished.** A strip under the alert line lists the last 10 conversations that finished their turn in the last 3 hours, newest first: when, account, name, repo and the first line of the final reply. Click one to see it in the panel. The chevron folds the strip, and it stays folded next time (`finishedOpen`).

**Selecting several conversations.** `Ctrl`+click a card, a wall tile or a map node to add it to the selection (or take it out); the first `Ctrl`+click takes the picked conversation along, so `Ctrl`+click on a second card makes two. On the map, `Shift`+drag on empty space draws a thin dashed rectangle and selects every conversation inside it. Selected cards and tiles get a steady dashed outline, selected map nodes a steady double ring; the selection is one list for every view. A plain click picks one conversation and clears it, and so does `Esc` (before anything else it would close). A right-click on a selected one opens the **N conversations** menu (see "Orders and teams"). With two or more selected, their chats share the panel's Chat tab, one under the other (three at most; "+N more selected" says how many are left out), each with its name bar, its own chat box and an ✕ that takes it out of the selection; the panel opens by itself for a new selection. A chat's toolbar row (attach, mode, model, mic, send) shows only in the one being typed in. Closing the panel clears the selection.

**More keys.** `w` opens **Since you looked** (below; the clock button in the header does the same). In the Map: `n` / `N` pan to the next / previous conversation that needs you and pick it; `k` cycles the map's lens (State, Cost, Account, Idle, Context; saved as `mapLens`); `Shift`+`1`–`9` saves the current pan and zoom as a view and `1`–`9` glides back to it (saved as `mapViews`); `t` opens the replay bar (`Space` plays and pauses while it is open, `Esc` closes it). The footer lists them.

**Since you looked.** A frosted card at the top centre that says what happened while you were away: who needs you now, what failed (checks, deploys, API errors, failed or stuck agents), the PRs merged and gone live, the conversations that finished (with the first line of their last reply), the busiest conversations, and the cost at API prices since then, in total and per account. Each section shows its newest five ("Show N more" opens the rest); a click on a row picks that conversation. It counts from the last time the page was in view (kept in the page's `localStorage` as `fv.lastSeen`, so it survives a restart of the window); the `1h` / `6h` / `24h` chips look further back. It opens by itself when the page comes back into view after 30 minutes or more away (or opens fresh after that long), and with `w` or the header's clock button. `Esc`, its × or a click outside closes it. It reads `GET /since`.

**Desktop notifications.** While the window is not focused, a new alert of the kinds that want you (a question, an API error, stalled, failed checks or deploy, a stuck agent, a conversation past its handoff size, a new conflict, a message between conversations that share no team) raises a Windows notification with the conversation's name and what happened; a click on it brings the window up and picks the conversation. Each alert is told once (`state.alerts`, numbered; the last one told is kept in `localStorage`), and nothing old is announced the first time. The page asks for permission once, on your first click or key. Turn them off (or on again) with **Turn off desktop notifications** on a right-click on empty space (`notify` in `~/.fleet-view.json`, on by default).

**Repos: one list.** The repo menu, the map's repo diamonds and the repos the cards, wall and finished strip show are one list. Every repo in it has its diamond and territory on the map, even with no conversation on it.

- **Remove a workspace** with the × on its row in the repo menu (or `Delete` on the picked row, or "Remove from list" on the row's right-click), or with **Remove workspace** on a repo's right-click (its diamond on the map, or a repo chip on a card or wall tile). It leaves every view at once: the menu, its map diamond, territory and conversations, its cards, wall tiles and finished rows. A toast offers **Undo** for 6 seconds (`u` in the open menu too). If it was the repo you were showing, the views switch to All workspaces. It comes back by itself, with its conversations, as soon as a conversation in it works again (a prompt or a reply after you removed it; a resumed session writing its cost to the log doesn't count). Continuing one of its removed conversations or starting a new session in it brings it back too. Kept in `settings.hiddenRepos`.
- **Move a conversation to another workspace** with **Move to workspace** on its right-click: a submenu of the other listed repos. A conversation stays in the workspace it was started in (the repo of its launch folder, or a workspace added by hand such as a scratchpad), even when it reads or edits another repo, for example a teammate's after **Work together**; only a conversation started outside any workspace (the home folder) goes where its tool calls point. The move wins over both, and a conversation picked up from its handoff stays in the repo it was moved to (it keeps its own copy of the move). A moved conversation also offers **Back to the workspace it started in**. A toast offers **Undo**. Kept in `settings.moved` (up to 500).
- **Rename a conversation** with **Rename** on its right-click (cards, wall tiles, map nodes, the finished strip): the menu turns into a text box with the current name. Enter saves, Esc cancels, and an empty box goes back to Claude Code's own title. In the panel, double-click the title, click the pencil beside it (shown on hover), or press **F2** anywhere in the panel except the live terminal: the title becomes the same box in place. A click elsewhere saves too.
- **The name wins everywhere.** Cards, map, wall, panel, alerts, the finished strip, Since you looked, the removed list, the mini window, the history and replay all show it, and so does the API. It is kept in `settings.names` (`{ <id>: name }`, up to 500), so it survives restarts. A conversation picked up from a handoff takes its predecessor's name unless it has one of its own.
- **Claude Code hears it too, when that is safe.** When the conversation runs in this window and Claude is idle, with no question or panel on screen and nothing typed in its prompt, Fleet View types `/rename <name>` into it the way the chat box sends. Otherwise only Fleet View's name changes, and the toast says why ("Claude Code keeps its own title (Claude is busy)"). Clearing a name types nothing. The toast offers **Undo**.
- **A new session can't be renamed yet.** It has no id until its first message, so **Rename** stays greyed out until then.
- Names are one line: spaces are collapsed, control characters dropped, and the name is cut at 80 characters.
- **Choose where a conversation's work goes** with **Push to** on its right-click: **Workspace default**, **Production** or **Preview**. Production is the standing rule (merge to main and ship); Preview pushes the branch for a preview build and doesn't merge (detailforge-web: a `[preview]` commit for the Vercel preview, the app on the `preview` EAS channel). A repo's right-click has the same **Push to** (Production by default, or Preview), which every conversation in it follows unless it has its own choice; a pickup of a conversation's handoff takes the conversation's choice. Kept in `settings.pushTargets`. The server writes the resolved list to `%LOCALAPPDATA%\fleet-view\push-targets.json`, and `scripts/push-target-hook.py` (a `UserPromptSubmit` and `SessionStart` hook in both accounts' `settings.json`) adds a line telling the conversation at every prompt when it's on Preview, or on Production in a Preview repo. The hook is not part of the shared copy, so the menus show **Push to** only when `scripts/push-target-hook.py` is in the Fleet View folder and an account's `settings.json` runs it (`/state` `tools.pushHook`).
- **No workspace.** Your home folder isn't a repo: conversations start there (the launchers' folder) and sit there until their tool calls point at a repo, so it is shown as **no workspace**, listed last in the repo menu and the Move to workspace submenu, and not remembered across restarts. Its conversations open in the plain `claude` Terminal window.
- **The map is remembered across restarts.** Every repo the map lists is kept in `settings.remembered.repos` and listed again at the next start, with or without conversations, until you remove it (or it goes unseen for 30 days). Every unfinished conversation it lists is kept in `settings.remembered.sessions`: at the next start it is read again whatever its age, and it stays while it was active in the last day, instead of leaving 45 minutes after it went quiet. A conversation leaves when it finishes, is removed or hands off.
- **Add a workspace** with **Add workspace**: the last row of the repo menu (or `a` while it is open), or a right-click on empty space (the map, or around the cards or wall tiles; there it is a submenu). It offers three ways:
  - **Paste path** (`p`): a path box, in the desktop window and in Edge alike ("Paste a folder path, e.g. Z:\Github\my-project"): type or paste the folder's path, `Enter` adds, `Esc` goes back, and if the server refuses it the reason shows in red under the box (the box stays, with your text). Quotes around the path (Explorer's "Copy as path") are dropped and forward slashes are fine (`Z:/Github/my-project`).
  - **New scratchpad** (`s`): makes a new empty folder, `scratch-YYYY-MM-DD` (then `-2`, `-3`…) under `%USERPROFILE%\Scratchpads` (`--scratch-dir` to change it), and adds it, for a session that needs no repo. It is marked trusted in each account's Claude Code config (`~/.claude.json`, `~/.claude-a/.claude.json`), so its first session does not open on "Do you trust the files in this folder?". The toast names the folder.
  - **Browse** (`b`): the system folder picker. Desktop window only; in Edge it is a quiet line.

  The folder must exist and its path may not hold `"`, `%`, `^`, `&`, `|`, `<`, `>` or a control character. A folder inside a git repo is added as that repo (its main checkout, for a worktree); any other folder is added as it is. The repo then shows in the menu and on the map (its diamond and territory, steady, with no conversations), so you can right-click it for **New session · A / B**. Adding a repo you removed brings it back. Removing an added repo also forgets it for good (Undo adds it back). Kept in `settings.addedRepos` (up to 100).
- **A repo's history comes back with it.** Removing a repo only hides it: its conversations' logs stay on disk and nothing about them is forgotten. Adding it back (or it coming back by itself) shows its live conversations and the ones that finished in the last 3 hours again at once. Conversations you removed one by one stay removed, and are under **Removed conversations ▸** as before.

**Opening a conversation** starts `claude --resume <id>` in a new tab of a Windows Terminal window named after its repo (`detailforge` for the detailforge repos), or in a console window of its own on a PC without Windows Terminal. Any conversation that hasn't finished probably still has its own window, so the first click only warns you; a second, separate click (or `o`) within five seconds opens a second copy anyway. A fast double-click doesn't count. `Esc` never quits; `q` does.

**Mouse on Windows.** Windows Terminal only sends clicks to a program as text when the console has virtual-terminal input turned on, and Node's raw mode leaves it off. At startup Fleet View runs a short PowerShell that turns it on (and turns QuickEdit off, so a click isn't taken as a text selection). Everything the mouse does also has a key, so if clicks still don't arrive the keyboard covers it.

## Live sessions in the panel

In the desktop window, the detail panel has five tabs: **Chat** (the one a picked conversation opens on), **Session**, **Changes** (its diff, to review; see below), **Preview** (its dev server; see below) and **Details**. Session hosts the real interactive Claude Code session for that conversation, the same screen as its terminal window, live and typeable.

- **Clicking a conversation starts its session.** A click on a card, a wall tile, a map node, a "recently finished" row or a mini-view row opens the panel on Session and runs `claude --resume <id>` there right away, in a pseudo-terminal (node-pty, ConPTY) inside the desktop app, in the conversation's folder and under its account (A sets `CLAUDE_CONFIG_DIR` to `~/.claude-a`). It is never headless. A session already running here is attached instead.
- **Preview sessions.** A session started by a click is a preview until you type or paste into it; the tab header says so in one dim line ("preview — closes when you move on unless you type"). When you pick another conversation or close the panel, previews end (Ctrl+C twice, then the process tree). A session you typed into, or opened on purpose (`Enter`, a double-click, **Open here**, **Open here anyway**), stays until you end it or close the window. The terminal doesn't take the keyboard on a click (the view's keys keep working); click into it to type. `Enter` and a double-click do give it the keyboard.
- **Open in another window.** `/state` marks a conversation `openElsewhere` when a live claude process has it open (its `sessions/<pid>.json`, with the pid checked alive, read on every server poll). Such a conversation is not started: the tab says it is open in another window, names the terminal tab to look for, and offers **Open here anyway** (two copies then write to the same log). Fleet View's own sessions write those files too; the page ignores the flag for the ones it hosts or just ended.
- **Arrow keys never start anything.** Moving the pick with the arrows (Cards, Wall, Map) shows the panel on Session with "Press Enter to open the session"; `Enter` starts it.
- **Sessions outlive the window.** They run in the session host (`desktop/host.js`), a small separate process, not in the window: closing the window, a server reload or a page reload never ends them. The window starts the host when it isn't running (`electron.exe host.js` with `ELECTRON_RUN_AS_NODE=1`, detached, no window) and connects to it before the page loads; reopening Fleet View reconnects and each session replays its screen (its last ~512 KB of output), with work mid-turn still going. Switching conversations keeps every session running; each keeps its own screen. The tray tooltip counts them ("2 sessions here").
- **Quit everything** (tray) is the one way to end them all at once. While sessions run it asks first: **Move to Terminal tabs** (**Move to console windows** when `wt` isn't on the PC), **Close them** or **Cancel** (and says which are mid-turn). **Move to Terminal tabs** ends them here as below, then opens each conversation as a tab of one new Windows Terminal window (`wt -w new`), in its folder and its account's tab colour, running `cmd /k claude --resume <id>`; for any account but B the command sets the account first (`set CLAUDE_CONFIG_DIR=%USERPROFILE%\.claude-<x>&&claude --resume <id>`), and an account with its own launcher (`%APPDATA%\npm\claude-a.cmd`) runs `claude-a --resume <id>` with the "Claude A" profile. It never goes through PowerShell, whose script policy can refuse npm's `claude.ps1`. Without Windows Terminal (or when `wt` won't start) each opens in a console window of its own (`cmd /c start`) with the same command. Fleet View's `CLAUDE*`/`NO_COLOR` variables are stripped. A moved one leaves the restore list only once its window started, so the next start doesn't open it twice and one that never opened is resumed then; a new conversation still without its id can't be resumed, so it stays on the list. Either way the host saves the restore list, ends every session (Ctrl+C twice, then the whole process tree after 2.5 s) and exits, and the app quits. The next start resumes every session that was open (`claude --resume`, new conversations too once they had their id; one still waiting for its id is dropped, and so is one another terminal has open by then). A reboot does the same from the last list the host wrote. A session that was mid-turn comes back with a quiet line in its Session tab, "Was interrupted when Fleet View closed — it carries on by itself once it has loaded". `claude --resume` starts no turn by itself, so once the resumed session has loaded and sat idle a few seconds (no menu or prompt on screen), the host types a one-line `[Fleet View] …` note into it: cut off mid-turn (check what finished, then carry on), or background tasks stopped (a resumed session that was idle gets this only when its log shows tasks the shutdown stopped), or restarted as asked (below). Typing into it first cancels the note, and the host gives up 3 minutes after the start. `"autoContinue": false` in `~/.fleet-view.json` turns it off (the line then says "tell it to continue").
- **The host.** It listens on the named pipe `\\.\pipe\fleet-view-host-<username>` (newline-delimited JSON; only one host at a time, the pipe name is the lock) and only answers a client that presents the random token in `%LOCALAPPDATA%\fleet-view\host.json` (`pid`, `pipe`, `token`, `startedAt`). It rewrites `%LOCALAPPDATA%\fleet-view\sessions.json` on every change (`[{ id, cwd, account, startedAt, busy, interrupted, cols, rows, pendingKey?, restartBy? }]` plus `ui: { selectedId, wide }`; `busy` also counts a prompt it waits on mid-turn; the window reselects that conversation when it reopens), logs to `%LOCALAPPDATA%\fleet-view\host.log`, and exits by itself only after 10 minutes with no session and no window. If it dies while the window is open, the window starts a new one, which resumes the sessions from the list. Updating `desktop/` restarts only the window; a changed `host.js` (or `handoff.js`, which it loads) takes effect the next time the host starts (it logs that a newer one is on disk). `node desktop\restart-host.js` restarts it safely: the host first checks that the `host.js` on disk loads (else it refuses and keeps running), answers at once, waits until no other session is mid-turn (at most 10 minutes; `--now` skips the wait), checks again, saves the list, ends the sessions and starts its successor, which resumes them (the one that asked gets a note to check the new version in `host.log`, and carries on). Exit code 0: asked (or no host running); 1: refused; 2: the running host is older than the restart op, so end it the old way once. While the host runs it holds node-pty's native module open, so end it (Quit everything) before reinstalling `desktop/node_modules`. Tests use `FV_HOST_PIPE` (another pipe, files in a `test-<name>` folder), and only such a host honours `FV_TERM_CMD`, `FV_HOST_SESSIONS_DIR`, `FV_HOST_IDLE_MS`, `FV_HOST_SETTINGS`, `FV_HOST_PROJECTS_DIR`, `FV_HOST_NUDGE_GIVEUP_MS` and `FV_HOST_PANEL_CLOSE_MS`; `node desktop\host-test.js` runs the host's own test against one.
- **Effort for new conversations.** A new conversation started from Fleet View runs `claude --effort medium`, so it never inherits the last `/effort` some other session saved as Claude Code's default. Set `"newSessionEffort"` in `~/.fleet-view.json` to `low`, `medium`, `high`, `xhigh` or `max`, or `"last"` for no flag (Claude Code's saved default). Forks and resumed conversations are left as they are.
- **`fv` in every session.** Each claude the host starts has the Fleet View folder first on its `PATH` (so `fv` works there even when the host started before `install.ps1` set the user PATH), and may run `fv send …` without a permission prompt: new, resumed, forked and picked-up sessions all start with `"--allowedTools=Bash(fv send:*)"`, so a message between teammates never waits on an approval click. Nothing else is allowed that way; the rest follows the account's own permission settings.
- **Send elsewhere ▸ Claude <letter>** (right-click a conversation) ends it here and resumes it under that account with `/handoff`, whose pickup carries on there. It is refused, with nothing ended, unless that login has the `/handoff` and `/pickup` commands (`skills/<name>/SKILL.md` or `commands/<name>.md`, in the login or the conversation's own `.claude` folder) and the conversation's log is in that login's `projects` folder; the toast says which is missing. An account with nothing left of its 5-hour or weekly limit (until it resets) isn't listed; with none left to offer, the item isn't shown.
- **Panels left open.** While a panel such as `/usage`, `/config` or a picker is open, Claude Code holds back background-task updates, so a session left like that stalls. The host notes a `/` command typed into a session (in the terminal or from Chat); when a panel follows it and nobody presses a key in that session for a minute, it closes it with Esc (`"panelAutoCloseSec"` in `~/.fleet-view.json`, `0` never). A panel no `/` command opened (a startup dialog such as trusting a folder, where Esc could refuse it) is left alone. While one is open, the Chat tab shows it as a card (or, when it can't read it from the screen, a note with **Close (Esc)**), and sending from Chat, a team order or `POST /api/sessions/<id>/message` closes a `/` panel first, then types; Chat sends one Esc at a time, never two together (two quick Escs at the prompt open Claude Code's rewind menu). Cards turn **NEEDS YOU** with "a panel is open in its terminal (like /usage)" for any live claude waiting like this, hosted or not.
- While the terminal has focus, Fleet View's single-key shortcuts are off and every key goes to Claude (Esc included). Ctrl+C copies a selection, otherwise it goes to Claude; Ctrl+V pastes; Shift+Enter adds a new line. "wider" widens the panel to 60% of the window.
- Conversations running here show a small "here" marker on cards and map labels.
- Closing the window asks nothing and ends nothing: the sessions keep running in the host (they are still there in any terminal view of them, and in the window when it opens again).
- The Edge window can't host sessions: there the panel opens on Details, clicks and `Enter` work as before (Enter or a double-click opens a Windows Terminal tab), and the Session tab offers the usual Open in terminal button.
- **New sessions.** Right-click a repo (see "Right-click menus") and pick **New session · A** or **New session · B**: the desktop window starts a plain interactive `claude` (no `--resume`) in that folder, under that account, with the same environment cleanup as any session it hosts. Only a folder `/state` lists (a repo root, an added repo, or a conversation's checkout) is accepted; the desktop app checks it against a fresh `GET /state`. The map shows a **new session** node at the repo at once (hollow, with a steady dashed ring in the account's colour), and the panel opens on its Chat tab with the cursor already in the chat box, so you can type the first message at once (a Fork does the same). Until Claude Code reports which conversation it is, the session is keyed `new-<n>`; as soon as Claude writes its `sessions/<pid>.json` (a few seconds after it starts, before any message) the desktop app re-keys it to that conversation id. The node stays a "new session" until the conversation's log exists (after your first message) and `/state` lists it; then the real node takes its place, in the same spot. A folder Claude Code hasn't been trusted in yet first asks "Is this a project you trust?" in the terminal, and it reports its id only once that is answered.
- **Remove** (right-click a conversation): ends its session if it runs here (Ctrl+C twice, then its whole process tree after 2.5 s; asks first when Claude is mid-turn), then takes it off the map, cards, wall and finished strip. Its log stays on disk, and it comes back by itself if it works again. A new session that never got a message is simply gone.

## Reviewing changes (the Changes tab)

The detail panel's **Changes** tab shows what a conversation changed in its repo as a diff you can comment on, like the review pane in the Claude desktop app. Your comments go back to Claude as one chat message.

- **What it compares.** The toggle at the top picks **Uncommitted** (what a commit would take now: staged and unstaged changes against `HEAD`, plus new files git doesn't ignore) or **Whole branch** (everything since the branch left main: its commits, what is uncommitted and new files, against the merge-base with `origin/HEAD`, else `origin/main`, `main` or `master`). The bar shows the file count, the total `+`/`−`, and the branch. The repo is the one git finds from the conversation's folder (its `cwd`, else its checkout). The choice is kept per conversation.
- **It keeps itself current.** While the tab shows, it reads the changes again every 3 seconds; **Refresh** reads them at once. Only what changed is redrawn: the scroll position, open files, comments and a half-typed comment all stay.
- **Files.** One row per file: the status (`M` changed, `A` added, `D` deleted, `R` renamed, `U` new and untracked), the path with its folder dim, and `+n −n`. Click a row (or focus it and press Enter) to open its diff: old and new line numbers, red and green rows, hunk headers and syntax colours. **Open** opens the file in VS Code at its first changed line. Binary files show no lines. A very big change is cut (2,000 lines a file, 20,000 in all, the first 512 KB of a new file) and says so.
- **Comments.** Click a line, or the `+` in its gutter, to write a comment under it. Enter saves, Shift+Enter starts a new line, Esc cancels. A comment shows under its line with **Edit** and **Delete**. With a diff focused, the arrow keys (or `j`/`k`) move a line cursor and Enter (or `c`) comments on that line. A comment whose line has left the diff moves to the end of its file (or below the list when the file is no longer changed) and is still sent.
- **Send to Claude.** The footer counts the comments. **Send to Claude** turns them into one message and sends it in the Chat tab at once, then clears them:

  ```
  Review comments on your changes (uncommitted):

  1. web/app.js:42 (+)
     > const x = load();
     why load it twice?
  ```

  `(+)` is an added line, `(-, old line)` a removed one (numbered as in the old file); context lines have no mark. **Clear** (press it twice) drops them without sending.
- **Kept until sent.** Comments are kept per conversation while the page lives, and in the page's `localStorage` (`fv.review.<id>`), so a reload keeps them.

### `GET /changes`

`GET /changes?cwd=<folder>&base=work|branch` answers `{ ok, root, branch, base, baseRef, files, truncated, sig, note? }`. Each file is `{ path, old, status: 'M'|'A'|'D'|'R'|'?', added, removed, binary, truncated, hunks: [{ header, lines: [{ t: ' '|'+'|'-', a, b, text }] }] }`, with paths relative to the repo root and `a`/`b` the old and new line numbers. `cwd` must be a full path inside a folder Fleet View knows (a conversation's folder or repo, or a remembered or added repo), else `403`. It runs `git diff` with no colour, no external diff and no textconv driver, and reads untracked files itself. An answer is kept for 2 seconds per repo and base; `&since=<sig>` returns `{ ok, same: true }` when nothing changed, and `&fresh=1` skips the cache. A folder outside git answers `{ ok: true, files: [], note: 'not a git repo' }`.

## Preview tab

The detail panel's **Preview** tab shows the conversation's running dev server next to the chat, like the Claude desktop app's preview pane: the page itself, live, with a small browser toolbar above it.

- **It finds the server by itself.** Fleet View reads the end of the conversation's transcript for local addresses Claude used or a dev server printed (`http://localhost:<port>`, `127.0.0.1`, `[::1]`; `0.0.0.0` counts as localhost; terminal colour codes are ignored, so Vite's bold port is found). One entry per port, newest first, each checked with a quick connect: a green dot answers, a red one doesn't. Fleet View's own port is never listed. With nothing picked yet, the newest address that answers opens.
- **The toolbar.** Back, forward and reload; the address box (type `localhost:3000`, `:5173/admin` or just `3000`, then Enter; only local dev servers show here); the list of servers (the chevron); **Open in browser**; and **Screenshot to chat** (desktop window). The address box follows the page: a link, a redirect or the app's own routing updates it. Back and forward load the earlier address again (the page's own history can't be reached across origins). The page you looked at last is remembered per conversation.
- **`.claude/launch.json`.** A folder with Claude desktop's `launch.json` (`{ "configurations": [{ "name", "runtimeExecutable", "runtimeArgs", "port", "url"?, "cwd"?, "env"? }] }`, comments allowed; a worktree without its own uses its repo's) lists its configurations under the found servers, with **Start** and **Stop**. Start runs it in the conversation's own folder (the worktree, when it is one) as a hidden background process (no window; `npm` and other `.cmd` launchers work), sets `PORT` to its port, and the tab says "Starting… waiting for <address>" until the page answers, then shows it. It keeps running when Fleet View's server restarts, and Stop still ends it then (its whole process tree, after checking it is still the process Fleet View started). Its output goes to `%LOCALAPPDATA%\fleet-view\preview-logs`. Starting one whose port already answers just shows it. Only folders Fleet View lists (conversation folders and repos) can be started.
- **Nothing running.** "Nothing answers at localhost:3000 right now" offers **Start** when a launch configuration owns that port, else **Ask Claude to start it**, which sends Claude "Start this project's dev server in the background (run_in_background) and tell me its local URL." With no server found at all, the tab shows the same choices in a card.
- **Screenshot to chat.** Takes a PNG of the page as the tab shows it and puts it in the chat box with "Screenshot of the preview at <address>:", unsent, so you can type your question first. Desktop window only (the button is hidden in Edge, and in a window started by an older `desktop/main.js` until it restarts).
- **Framing.** Dev servers often forbid being shown inside another page (`X-Frame-Options`, CSP `frame-ancestors`). The desktop window drops those two headers, and only them, for a local dev server's page inside the Fleet View page (not for anything else, not for other windows). The page runs sandboxed: scripts, forms, its own storage and cookies, popups and dialogs work; it can't navigate the Fleet View page away; links that open a new window open in your default browser. In Edge the frame shows only pages that allow framing; when one doesn't, a quiet line says so and offers **Open in browser**.
- **Sign-ins.** The Fleet View page is `127.0.0.1`, so a dev server at `localhost` is another site to the browser, and cookies that default to `SameSite=Lax` aren't sent inside the frame. If a sign-in doesn't stick in the preview, type the address with `127.0.0.1` instead of `localhost` (when the server listens there).
- **Server side.** `GET /preview/urls?id=<conversation>&cwd=<folder>[&current=<url>][&frame=1]` answers `{ urls: [{ url, from: "transcript", at, up } | { name, port, url, from: "launch.json", launch: true, running, up }], current?: { url, up, frame? } }`; `POST /preview/start` and `POST /preview/stop` take `{ cwd, name }`. A request from any page but Fleet View's own (another `Origin`, such as the previewed dev page) is refused.

## Chat box extras

- **Files open in Fleet View.** A file path in the chat opens in Fleet View's own viewer instead of VS Code: the file name on a Read, Edit, Write, MultiEdit or NotebookEdit row (and the "file" line when the row is open), the paths a Grep or Glob printed (with Grep's line numbers), and inline code in a reply that looks like a path (`web/chat.js`, `chat.js:120`, `a.ts#L12`, `C:\x\y.txt`, `web/`). A path counts when it has a known extension, is absolute, or is a folder with a trailing slash; `/compact`, `origin/main`, `/api/sessions` and URLs stay plain. These are links at once; whether the file is there is asked only when you click (a toast says when it isn't). **Ctrl+click** (Cmd+click) opens VS Code instead, as before.
- **The viewer.** A large frosted window over the page: the path, the lines numbered and highlighted, scrolled to the line and marked in gold. An Edit row opens at its new text, a Read row at the line it started from, `path:line` at that line. A folder lists what is in it (click one to open it, `..` goes up); a picture shows as itself; a binary file only says so; a text file over 1 MB shows its first 1 MB. **Copy path**, **Open in VS Code** (a folder: **Open in Explorer**, at the marked line) and **Close**. Esc or a click beside the window closes it. Ctrl+F (find in page) searches only the file while it is open.
- **What it may read.** `GET /file?path=<abs or relative>&cwd=<folder>` serves only what lies inside a folder Fleet View knows (every conversation's folder and repo, the remembered and added repos; case-insensitive, links resolved first); anything else gets `403`, a missing file `404`. A relative path is read against the conversation's folder; `/c/Users/…` (Git Bash) and `~` work too. `&raw=1` gives a picture's bytes (PNG, JPEG, GIF, WebP, SVG; an SVG is sandboxed, no script runs). A request from another site is refused. `.credentials.json` is never served.
- **Bash mode.** Type `!` as the first character of an empty chat box and the box turns into a shell command: a "! bash" tag, monospace, a rose border. Send types `!` into the session as a key of its own (Claude Code switches to bash mode only on a typed `!`, never a pasted one), then pastes the command and presses Enter: it runs in the session's shell and its output goes into the conversation. Backspace or Esc in the empty box leaves bash mode; a pasted `!` stays text. The feed shows the command as "! command" and its output as a block under it; ↑ and Ctrl+R bring a past command back in bash mode. Claude Code's old `#` for adding a memory is gone from it (2.1.x has only the prompt and bash modes), so the box has no `#` mode.
- **Ctrl+R** in the chat box searches your past messages in the conversation (the list ↑ goes through): newest first, filtered as you type (every word, any case); ↑↓ pick, Enter (or Tab) puts it in the box, Ctrl+R again moves to the next, Esc closes. (The desktop window reloads on F5 or Ctrl+Shift+R, so Ctrl+R is free for this.)
- **Ctrl+B / Run in background.** While Claude runs a shell command that can go to the background (its screen says "ctrl+b to run in background"), the activity line shows **Run in background**, and Ctrl+B anywhere in the Chat tab does the same: it sends Ctrl+B to the session.
- **Ctrl+O / Expand all.** Ctrl+O anywhere in the Chat tab (the chat box too) opens every tool row and thinking row, like the terminal's transcript view; Ctrl+O again closes them back to how they were. The same toggle sits at the top right of the feed (it shows while you point at the feed, and stays while it is on).
- **Handed to the chat box.** Review comments from Changes and a screenshot from Preview arrive in the chat box: the text after what is already typed (a blank line between), the pictures as attachments (uploaded on send, like a pasted screenshot), and the focus in the box. One marked to send goes at once, the way Send does.
- **The mic.** The mic button by Send lets you talk instead of type. It listens until you click it again. Whisper runs on this PC, in the page (`web/voice.js`, `web/voice-worker.js`): the small English model on the graphics card (WebGPU), or the base one on the CPU. The first click downloads the model once (about 400 MB; a line under the box shows the progress), then it comes from the browser's cache. Nothing you say leaves the machine. Speech is cut at your pauses, and each stretch goes in after what is in the box. Clicking the mic to stop still writes out what you said up to then. Sending, or switching the box to another conversation, stops it at once and drops what was not written yet.
- **You see what you say while you say it.** About every second, the stretch you are in the middle of is written out again and shown in grey italics after the text, right where it will go. When you pause, the final text takes its place (it often fixes a word or two, and adds the punctuation). The preview is never part of the message: the draft, Send and ↑ only ever see the final words. You can keep typing while you talk; the preview moves along after what you type. A preview only runs when Whisper has nothing else to do, so it never holds up the final text. On a slow PC it backs off to every 2 or 3 seconds, and turns itself off until the next mic click if even that is too slow. On the CPU model it starts at every 3 seconds.

## Session handoffs

Long conversations checkpoint themselves at about 200k context tokens (`limitTokens` in `%USERPROFILE%\.claude-handoffs\config.json`): a Stop hook has Claude write a handoff summary there, and whatever launched claude starts a fresh conversation that runs `/pickup <file>`. The hooks and launchers live outside this repo; `handoff.js` reads what they leave (`FV_HANDOFF_DIR` points it at another folder, for tests).

- **Sessions in the panel.** The session host gives every claude it starts its own `CLAUDE_LAUNCH_KEY` (`fv-<uuid>`). When one asks for a restart (`.restart/<key>.json`) and is killed, the host takes the request and starts `claude "/pickup <file>"` in its place: same account, the request's folder, the old screen kept above the new one, and no "Session ended". Once the new claude writes its `sessions/<pid>.json` the host re-keys it to the new conversation id, and the panel, its terminal and the selection follow. A session you end (Remove, Quit everything) never restarts. A pickup that had no id yet when the host stopped is restored as the conversation it started (when the handoff names it) or by running the pickup again.
- **Terminal tabs.** "Open in terminal" runs `claude-a.cmd --resume <id>` / `claude-b.cmd --resume <id>` (from `%APPDATA%\npm`) instead of the bare `claude`, so a handoff restarts in that tab (and `/swap` works there). Without the launcher it runs `claude`, with the account set in the command itself for any account but B (`set CLAUDE_CONFIG_DIR=%USERPROFILE%\.claude-<letter>&&claude --resume <id>`), since a Windows Terminal that is already open makes the tab itself. On a PC without Windows Terminal (Windows 10 until it is installed) it opens a console window instead (`cmd /c start … cmd /k …`).
- **Cards and the panel.** A conversation that handed off shows "handed off → <new one>", the new one "picked up from <old one>"; both names are links that pick that conversation (or open its panel when it has finished). Beside "picked up from", **Chat** and **Summary** open the previous conversation under the new one's chat, in the same panel: its chat read only (no chat box, no Rewind, Edit or Reply), or the handoff summary (the `.md`, drawn as markdown, without its front matter). The bar over it switches between the two, and its ✕ closes it; it does not come back on the map and nothing starts. The new one's right-click has the same under **Previous conversation ▸**. The link comes from the handoff file (`next_session`), its `.state/<id>.json`, or the new conversation's own `/pickup <file>`. A handed-off conversation whose claude is gone counts as finished, even though it was killed mid-turn. Next to the context gauge, cards and the panel show the context against the handoff size ("182k / 200k").

## Code graphs (CodeGraph)

With [CodeGraph](https://github.com/colbymchenry/codegraph) installed (`npm install -g @colbymchenry/codegraph`), Fleet View indexes every repo it lists, and the checkout of every conversation active in the last day (worktrees included), so Claude can answer "who calls this, what does a change here touch" from the graph instead of grepping. It is local and free: no API key and no model calls. Without `codegraph` on PATH nothing happens. (`codegraph.js`)

- **Indexes.** Each checkout, worktrees included, keeps its index in `.codegraph\`, which is added to the repo's `.git\info\exclude`. Indexes are built one at a time at below-normal priority, about 3 minutes for a large repo. Once built, the MCP server keeps an index up to date by itself. Until a worktree's own index is built, CodeGraph answers from the main checkout's, because it searches parent folders. The log is `%LOCALAPPDATA%\fleet-view\codegraph.log`.
- **Connecting Claude Code.** Add CodeGraph once per account as a user-wide MCP server in `.claude.json`: `"codegraph": { "type": "stdio", "command": "cmd", "args": ["/c", "codegraph", "serve", "--mcp"], "env": { "CODEGRAPH_PROJECT_IDLE_TIMEOUT_MS": "20000", "CODEGRAPH_DAEMON_IDLE_TIMEOUT_MS": "30000" }, "alwaysLoad": true }`, and allow `mcp__codegraph__*` in `settings.json`. `alwaysLoad` loads the tool from the first prompt; otherwise Claude Code hides MCP tools behind a search and sessions rarely use them. The short idle timeouts make CodeGraph close a worktree's index 20 seconds after its last query; while the index is open, Windows won't let `git worktree remove` delete it.

### Orders and teams

An order is one text sent to several conversations at once. It is typed into each one's real, interactive session in this window, exactly as the chat box sends a message (the session is started here first if it isn't running, then the text goes in as a paste and Enter); Fleet View never starts a headless `claude` for it. So orders need the desktop window; in Edge the items say so.

- **Give orders ▸ Prompt** on a repo's right-click (the same submenu sets Model, Effort and Fast mode for all of them; its nested lists open in the submenu's place, with a back row): the order goes to every unfinished conversation in that repo. With two or more they become **one team** (`POST /teams`, named after the repo and the order's first words), so each gets, under the order, the list of its teammates (name, id, repo, branch) and the command to talk to them: `fv send <their id> "message" --from <its id>`, with "agree who changes which files before editing, tell them when you push or merge, and reply to their messages". A new session that has no id yet is waited on for up to 30 seconds; one that still has none joins the team once it has (it gets the order then), and with fewer than two ids there is no team, only the message. With one it is a plain message. The count is the conversations it can reach; one open in another window (a terminal elsewhere) can't be typed into from here, so it is left out and named in the item's note. With none the items are a quiet line saying why.
- **Work together** (several selected) does the same for the selection: exactly those become one team (any of them in another team leaves it, and that team is told), the order with the teammates list. The same set as a team that is there already gets the new order. **Send to each** sends the same text to each.
- **Message the team** sends a text to every member (not the ones removed from the map), starting with `[Fleet View · team "<name>"]`.
- **Add to team** (a conversation's menu, a selection's, or the team's **Add <picked>**) puts it in the team: the team keeps its colour, order and messages, the newcomer gets the order with its teammates, and the others a note with every member's id, the newcomer's too. A conversation in another team leaves that one. **Leave team**, **Remove member** and **Remove conversation** take one out: it is told it left (or was taken out; not when it was removed from the map), the rest get a note with the ids that are left, and a team left with one member is disbanded (that one is told so). **Disband team** ends the team; each member is told, and they keep working.
- A member that hands off, or runs `/clear`, is followed: the conversation that carries on takes its place in the team and gets the order, and the others are told its new id ("X handed off; Y (id …) carries on its part. Message that id from now on.").
- Notes about who joined or left go only to conversations running now (each one costs Claude a turn); orders and messages resume one that isn't running. The toasts count who was told ("Added X to "t" · told 2").
- **Send a note to all** on a conflict or shared file: each one gets the note, the others' names and ids, and the `fv send` command, so they can sort it out between them.

The box is a few lines tall: `Enter` sends, `Shift`+`Enter` starts a new line, `Esc` closes. The menu closes at once and a toast says it is sending; a second toast says how it went ("Sent to 3 conversations · team …", and which ones were not reached and why). A conversation is skipped, and named in that toast, when another window has it open or it handed off (give it to the one that carries on). One where Claude is showing a question or a permission prompt (the text would land in it) gets the order once that is answered: it waits, for up to 2 hours, and the toast says so; **Cancel waiting order** on its right-click drops it. Teams show on the map as links between their members (see "Map command center") and are described under **Teams** below.

## The app window's server

**The server belongs to the app.** With the desktop window installed, `fleet-view` (and the sign-in shortcut) only starts the app; the app starts the server hidden (no console window), restarts it after an update or a crash, and stops it when the app quits. A server that was already running (started some other way) is used as it is and left alone. When the app's server doesn't answer within 20 seconds (an `electron.exe` that won't start: blocked by antivirus, a graphics crash, a damaged download), the launch goes on as the server itself with the Edge window, so it never ends with nothing running (`server.log` says why). `--no-open`, `--demo` and `--tui` still run the server in the console as before.


Everything is served on 127.0.0.1 only, and requests from other sites are refused (the `Host` must be this address and a browser `Origin` must be the page's own). The automation API under `/api/` takes no `Origin` at all and needs its token instead (see "Automation API" below).

| request | |
|---|---|
| `GET /`, `GET /<file>` | the page, from `web/` (html, js, css, svg, png); nothing outside `web/` |
| `GET /state` | everything the page draws, as JSON, computed fresh on each request: header counts, alert, `repos` (the one repo list: every repo with a conversation in the window, plus the added ones, less the removed ones; `{ root, name, live, color, added? }`), every conversation in the window (state, account, model, context use, branch, worktree, goal, last action, what it is waiting on, progress, agents, ship track, plan steps, files touched, tokens and cost, sparkline), files two conversations touched, the latest tool calls, and `finished` (see below) |
| `POST /open` `{"id"}` | opens that conversation in a Windows Terminal tab, or a console window on a PC without Windows Terminal (the page confirms first); replies `{"ok","message"}` once the window's program started (or could not). A conversation that is no longer in the window opens from its log too: any one in the history index (the Projects view's Older conversations), and a removed one while it is on the hidden list or for 2 minutes after it left it (Continue) |

**Production deploys.** The map shows each repo's production deploy on its hub, for every repo on the map that deploys (Vercel or any host that reports to GitHub). A small Vercel triangle badge sits at the hub's upper right: gold with a gold arc turning round the hub while a build runs, mint when Vercel is clean (nothing building, the last deploy live), red with a thin red ring when the last deploy failed. Repos that don't deploy get no badge. The hub's tooltip says which, with the time ("building · started 1m ago", "clean, nothing building · last live 21m ago") and the commit's PR and title; the legend (`l`) lists the three looks. The server reads them with `gh`: `repos/<slug>/deployments?environment=Production` and each one's newest status (success is live, failure or error failed, inactive left out, none yet or pending building), plus the `Vercel` commit status on the default branch's newest commit, because Vercel writes the deployment only once the build is done (pending there is building). Each commit's title and build start are read once and kept. A repo is asked every 15 seconds while one of its deploys builds or a conversation in it pushed or saw its PR merge in the last 10 minutes, else every minute, one repo at a time in the background. When one that was building goes live it raises a `live` alert ("<repo> is live on production (<title>)"), when it fails a `deployFail` one, once per commit: a PR's own "is live on production" alert and this one never both fire, and a PR's ship track reads the same lookups instead of asking GitHub again. Off with `--no-github`; in `--demo` storefront-web builds for 90 seconds, is live for 2 minutes, then builds the next one, and docs has a failed one.

**Parity.** A repo with a parity rule ships every change users see on the website and in the phone app together. Built in: any repo whose folder is named `detailforge-web`, where `mobile/` is the app, `packages/core/` is shared code, and `app/`, `components/`, `src/`, `lib/` and `public/` are the website. `settings.parity` (`[{ name, web: [prefixes], app: [prefixes], core: [prefixes] }]`, at most 20; a rule needs `web` and `app`) adds rules by folder name or replaces the built-in one; a file belongs to the first side, in the order app, core, web, whose prefix it starts with.

**Teams.** A team is a set of conversations told to work together (the page's right-click "Work together"): the order, who is in it, and the messages between them. Teams are kept in `~/.fleet-view.json` (at most 50, of up to 12 members each) and dropped once every member has been gone from the session list for 24 hours. Members talk to each other with `fv send <their id> "text" --from <my id>` (every session Fleet View starts has `fv` on its `PATH` and may run `fv send` without asking). It calls `POST /api/sessions/<to>/message` with `from`: the text goes in after a line `[Message from teammate "<name>" (<id>). Reply with: fv send <id> "message" --from <receiver id>]` ("teammate" only when the two share a team), and the server records it (in the team's messages when both are in one, as a feed entry with `to`, and as a `message` alert when they share no team, at most one per sender and receiver every 10 minutes). A receiver that handed off or ran `/clear` gets it in the conversation that carries on (`fv` says "sent to <new> (it picked up <old>)"); one showing a question or a prompt gets it once that is answered (`202`, "queued"); one not running in Fleet View is resumed in the desktop app first (`--no-open` refuses instead), unless it is open in a terminal outside Fleet View (`409`). Waiting messages are kept in `%LOCALAPPDATA%\fleet-view\msg-queue.json`, so a restart carries on with them, by the page's rules: one goes in 1.5 s after no menu shows, and is dropped after 2 hours, or after 5 minutes with its conversation not running. The older `node scripts/fleet-msg.js --from <my id> --to <their id> "text"` (in briefs from before) still works the same way (`--no-open`, `--wait <s>`, `--port <n>`, `--list`).

**Timeline.** A frame (the fields above for every conversation `/state` lists) is taken every 60 seconds, and after any conversation changes state (at most every 10 seconds). Frames are held as deltas (a full keyframe every 10 minutes, then only the conversations that changed), with every feed entry (at most 30,000) and the ship events, for 24 hours. They are appended to `%LOCALAPPDATA%\fleet-view\timeline.jsonl` every 10 seconds, so a restart keeps them; at start the file is read back and rewritten with the last 24 hours only, and it is compacted again when it passes 30 MB (a day too busy for that loses its oldest frames first). Not written in `--demo` (which makes up the last hour) or `--tui`.

`removed` lists the 50 most recently removed conversations (`settings.hidden`), newest first: `{ id, name, account, repo, cwd, removedAt, lastActive }`, where `repo` is `{ name, root, color }` or `null` and `lastActive` is when its log last changed. One still in the window uses what `/state` knows of it; an older one is read from its log once (`<id>.jsonl` under either account's `projects` folder; read again only when the log changes): its name is its custom title, else its AI title, else its first typed prompt (60 characters), `cwd` the folder of its last message, `account` the account whose folder holds it (or its running process's). An id whose log is gone is left out (it stays in the settings). At most 12 logs (64 MB) are read per request, so a long list fills in over a few seconds. In `--demo` it is empty.

**The history index** (for the Projects view's Older conversations) covers every conversation log in both accounts' `projects` folders, whatever its age: per log its id, mtime, name (custom title, else AI title, else its first typed prompt, 60 characters), last folder, account and repo. Its repo is the one its tool calls point into most (the files it read or edited and the paths in its shell commands, like the live view's repo; at most the first 256 KB and the last 2 MB of a big log are read), else the git repo of its last folder, so a conversation started in your home folder that worked in a repo counts for that repo. The server builds it in the background, two logs every quarter second on its own timer (never while answering `/state`), lists the folders again every 30 seconds and reads a log again only when its mtime changed. It is saved to `%LOCALAPPDATA%\fleet-view\history.json` (by log path and mtime), so after a restart only new or changed logs are read. Not built in `--demo` or `--tui`.

`finished` lists the last 10 conversations that finished their turn (`DONE`) in the last 3 hours, newest first: `{ id, name, account, repo, endedAt, summary }`, where `summary` is the first line of the final reply that says something (no headings, code or table borders), up to 140 characters. Each stays in `sessions` for those 3 hours, even after it leaves the `--window`, so the page can open its detail panel. When Fleet View starts it also reads logs older than the window but younger than 3 hours, and keeps the ones that end on a finished turn.

**Chat feed** (`conversation.js`). `GET /conversation?id=<id>` reads a conversation's log (one in the window, else any `<id>.jsonl` under either account's `projects` folder, the newer if both have one) and replies `{ id, total, from, items }`: `items` is the chat from index `from` on, `total` the count of all of it. With no other argument it is the last 300. `since=<n>` (the `total` a poll had) sends from `n - 12`, so a growing reply or a tool result that came in since is sent again; it starts earlier for a tool whose result came in the last 30 seconds (up to 200 items back), and at most 2000 items are sent, so the page replaces its list from `from` on, whatever `from` is. `before=<k>&limit=<m>` sends items `k - m` up to `k` (at most 1000) for "show earlier". Each item has a stable `key` and `t` (ms, or `null`): `user` (`text`, and `images` as links to `GET /conversation/image?id&key&n`, which serves that prompt image's bytes, each up to 4 MB, else `{ omitted: true }`), `assistant` (`text`, Markdown; the text blocks of one reply joined), `thinking` (only when it has text), `tool` (`id`, `name`, `input` with every string capped at 20,000 characters, `result`: `null` while it runs, then `{ text, isError }`, images in it as `[image]`), and `note` (a slash command run, as `/model opus`; an interruption; a compaction summary; an API error, retries folded into one; a background task's summary). Agents' lines, meta records, `<system-reminder>` and local command output are left out. The server keeps an index per log, not the conversation: each item's place in the file, read again for the items a request sends, so images and tool output are not held between requests. A log is read the first time in 8 MB chunks without stopping the server (a 400 MB log takes 2 to 3 seconds), then only what was appended; one that shrank or was replaced is read again. At most 6 logs are indexed at once. In `--demo` it is `web/fixtures/conversation-sample.json` when that exists, else empty. `POST /chat/image` `{ data: <base64>, mime: "image/png" | "image/jpeg" | "image/gif" | "image/webp" }` checks that the bytes start like that type and are at most 15 MB, saves them as `%LOCALAPPDATA%\fleet-view\chat-images\<16 hex>.<ext>`, deletes the images there older than 7 days, and replies `{ path }` (else `400` with `error`), so a prompt can name the file for Claude Code to read.

**Test-only switches.** `FV_TEST_CRASH=1` makes the server throw an exception nothing catches 3 seconds after it starts, to check the crash log and the restart loop (run `fleet-view.cmd` with `FLEET_VIEW_CHILD=1` to keep the loop in your console). `FV_TEST_NO_LAUNCH=1` makes `POST /open` write `test launch: <id> …` to `server.log` instead of opening a window. `FV_STARTUP_DIR=<folder>` makes `--install-startup`, `--remove-startup` and `settings.autostart` use that folder instead of the real Startup folder. On the page, `?fixture=1&fakeTerm=1` adds a stand-in for the desktop window's live sessions (it echoes what you type and prints some coloured output, starts new sessions and gives them an id after 1.5 s), to try the Session tab and the menus in any browser; without `fixture=1` it does nothing. `?fixture=1` or `?debug=1` adds `window.__mapNodes()` (every map node with its position in window pixels) and `window.__fv` (the page's state, for tests); with `?fixture=1` nothing is posted and the POSTs are kept in `window.__fvPosts`. `FV_TEST_HIDDEN=1` starts the desktop window hidden for tests driven through `--remote-debugging-port`: it never shows or takes focus, has no mini view, tray icon or blur helper, and Quit everything asks nothing and takes **Close them**.

### Automation API

A script on this machine can drive the live sessions the desktop app hosts: start one with a prompt, send it follow-ups, read its status and latest reply, and stop it. It works through the session host, exactly like the panel's Session tab, so every session it starts is a real interactive `claude` you can watch and type into in the panel. It needs the desktop app running; the server never starts the session host itself, and without it every request answers `503` "the Fleet View desktop app is not running".

**The token.** Every `/api/` request needs `Authorization: Bearer <token>`. The token is in `%LOCALAPPDATA%\fleet-view\api-token`, made the first time the server starts (32 random bytes as hex). Anything that can read your own folder can use the API, the same rule as the session host's `host.json`. The token is never logged, served or put in `/state`; delete the file and restart Fleet View for a new one. A request that carries an `Origin` header is refused (`403`), so no web page can use the API, not even Fleet View's own. A missing or wrong token gets `401`.

**Requests.** A session is named by its conversation id, or by the `new-<n>` key it had before Claude Code reported its id (the key keeps working until the session host restarts).

- `POST /api/sessions` `{"repo","account","prompt","chrome"?,"wait"?}` (more fields below) starts a plain interactive `claude` in `repo` under account `"A"` or `"B"`. `repo` follows the rule for the window's **New session**: an absolute folder, free of `"%^&|<>` and control characters, that exists and that `/state` lists (a repo root or a conversation's checkout); else `400` or `403`. It waits up to 60 s for Claude Code to report its conversation id and be idle, then pastes the prompt (as a bracketed paste, so new lines stay in the prompt) and presses Enter. Replies `{"ok":true,"key","id","chromeApplied","promptSent":true,"taken","done","message"}`, plus the reply when it waited (below). When it is not ready in time (a folder Claude Code has not been trusted in yet asks first, in the terminal), nothing is typed and the session keeps running in the panel: `{"ok":false,"key","id":null or the id,"promptSent":false,"message"}`. `chrome: true` starts it with `--chrome`, `false` with `--no-chrome` (Claude in Chrome on or off); left out, the account's own setting applies. `chromeApplied` is `false` when the running session host is older than this change and ignored the flag (it takes effect after the host restarts, below), and `null` when `chrome` was not given.
- `POST /api/sessions` also takes, all optional:
  - `"name"` (1 to 80 characters, no control characters): the conversation's name in Fleet View, the same as the page's **Rename**, set once its id is known.
  - `"model"` (letters, digits and `.-[]`, at most 60, like `"sonnet"` or `"opus[1m]"`) and `"effort"` (`"low"`, `"medium"`, `"high"`, `"xhigh"` or `"max"`): passed to the session host, which starts `claude --model <m> --effort <e>`: they apply to this session only (typing `/model` or `/effort` would save them as the default for every new session). The reply echoes `model` and `effort`; a session host too old to take them stops the session it started and answers `502`.
  - `"forkFrom": "<conversation id>"`: the new session starts as a fork of that conversation (`claude --resume <id> --fork-session`), which must exist on disk; the prompt goes in as usual.
  - `"temp": true`: a throwaway session, taken off the map (the hidden list) as soon as it is stopped or ends. Fleet View keeps the temp ids in `~/.fleet-view.json` (`apiTemp`, at most 200), so a restart doesn't forget them, and its regular scan hides any whose session is gone.
- `POST /api/sessions/<id>/message` `{"text","wait"?}` pastes the text into the session's prompt and presses Enter. Replies `{"ok","id","status","taken","done","message"}`, where `status` is the session's state just before: `"busy"` means Claude was mid-turn and Claude Code queues the message behind it, `"idle"` that it starts a turn now. `404` when no such session is hosted, `409` when it has ended, and `409` with `"menu": true` ("Claude is asking something: answer it first") while it shows a select menu: a permission prompt, a question or the plan approval, which the Enter would answer. The screen is read (its output played into a small terminal grid, `screen.js`) before the paste and again just before the Enter; a menu that comes up in between leaves the text in the prompt box, unsent. A panel a `/` command opened (like `/usage`) is closed with Esc first; any other open panel, or one that won't close, answers `409` with `"panel": true`. `"from": "<conversation id>"` makes it a message from that conversation: the text goes in after a first line `[Message from teammate "<its name>" (<its id>). Reply with: …]`, and the server records it (see **Teams**); `from` must be a conversation Fleet View knows (one that handed off counts as the one that carries on), and a conversation cannot message itself (`400`). `"queue": true` lets a message for a session showing a menu wait and go in once it is answered (`202` with `"queued": true`) instead of the `409`; `"open": true` resumes a conversation that is not running here first (as `open` below), and refuses with `409` `"elsewhere": true` when it is open in a terminal outside Fleet View. Both default to `true` with `from` and `false` without. A message for a conversation that handed off or ran `/clear` goes to the one that carries on, and the reply has `"redirected": {"from","to"}`.
- `GET /api/sessions` lists the hosted sessions: `{"ok","sessions":[...]}`, each as below.
- `GET /api/sessions/<id>` replies `{"ok","id","key","alive","status","pending","exitCode","name","state","label","lastReply","waitingOn","endedAt","cwd","account"}`: `status` is the session host's `"busy"` or `"idle"` (from Claude Code's pid file), and `state`, `label`, `lastReply`, `waitingOn` and `endedAt` are the conversation as `/state` shows it (`null` until its log exists, after the first message). `turn` is `{"startedAt","endedAt","open"}` (ms; `endedAt` is `null` while the turn runs), from the transcript. `?tail=<n>` (at most 20000) adds `tail`, the last `n` characters of its terminal output with the escape sequences taken out.
- `POST /api/sessions/<id>/stop` ends the session the way the panel does (Ctrl+C twice, then its process tree). Replies `{"ok","id"}`.
- `POST /api/sessions/<id>/stop` `{"remove": true}` also hides it from the map (the hidden list), temp or not.
- `POST /api/sessions/<id>/remove` hides any conversation Fleet View knows from the map, hosted or not, like the page's right-click **Remove**: it comes back if it works again. `409` while it is hosted and still running (stop it first, or use stop with `"remove": true`). Logs are never deleted.
- `POST /api/sessions/<id>/interrupt` presses Esc once, to stop Claude mid-turn. `409` when it is not busy, or while a menu is up (the Esc would answer it: use `answer` with `"option": "esc"`). Replies `{"ok","id"}`.
- `POST /api/sessions/<id>/wait` `{"timeout"?}` (seconds, 1 to 3600, default 1800) sends nothing and waits until the session is ready for you. When it already is (running, not busy, its turn closed, no menu up) it answers at once with `{"done":true,"endedBy":"idle","reply"}`; else it answers when `endedBy` is `"reply"`, `"question"`, `"menu"` (with `menu`, below), `"apiError"`, `"exit"` or `"gone"`, or with `"timedOut": true`. Hanging up stops the wait.
- `POST /api/sessions/<id>/open` `{"account"?,"prompt"?,"wait"?}` resumes an existing conversation (one Fleet View knows, whose log exists) as a hosted session in the desktop app, in its own folder and under its own account (`account` overrides). The folder must pass the same rule as start. One already running in the host answers `{"ok":true,"alreadyRunning":true}`; one open in a terminal outside Fleet View is refused (`409`, `"elsewhere": true`), since it would run twice. It waits up to 60 s for it to be idle; with `prompt` it then sends it the way a message does (and `wait` works the same).
- `GET /api/sessions/<id>/transcript?since=<n>&limit=<m>` reads any conversation Fleet View knows, hosted or not, from its log (the parser the panel's Chat uses): `{"ok","id","total","from","items":[{"i","type","t","text"?,"tool"?}]}`, where `type` is `"user"`, `"assistant"`, `"tool"`, `"note"` or `"thinking"`, `text` is at most 4000 characters, and `tool` is `{"name","input","result","isError"}` (`input` a one-line summary of at most 300 characters, `result` at most 2000). The last 50 items by default; `limit` at most 500; `since=<n>` gives the items from `n` on, so a caller can follow it with the `total` it saw last.
- `GET /api/conversations?state=<STATE>&repo=<text>&all=1&limit=<n>` lists every conversation Fleet View shows, not only the hosted ones: `{"ok","conversations":[{"id","name","state","label","hosted","alive","account","repo","branch","cwd","lastReply","waitingOn","active","pr"}]}` (`repo` its root folder or `null`, `lastReply` at most 500 characters, `active` when it last worked in ms, `pr` a number or `null`). `state` keeps one state (like `QUESTION`), `repo` the ones whose root contains that text; hidden ones are left out unless `all=1`. At most 100 unless `limit` says otherwise.
- `GET /api` describes the API itself: `{"ok","version":2,"endpoints":[{"method","path","body"?,"does"}]}`, so a script or a Claude can find what is there.

**Teams.** The same teams the page's **Work together** makes (see "Orders and teams"); each call sends the same briefs and notes the page does, and replies with what it told each member (`told` or `sent`: `[{ id, name, ok, queued?, message }]`). A team is named by its id (`t` and hex, from `GET /api/teams`).

- `GET /api/teams` replies `{"ok","teams":[...]}`: each team as `/state` lists it, plus `roster`, its members' `{ id, name, repo, branch, state, removed }`.
- `POST /api/teams` `{"members","order","name"?}` makes a team of exactly these 2 to 12 conversations, as `POST /teams` does, and sends each member its brief (resuming one that isn't running). Replies as `POST /teams`, plus `sent`.
- `POST /api/teams/<id>/add` `{"member"}` adds one; `POST /api/teams/<id>/remove` `{"member"}` takes one out (it and the others are told); `POST /api/teams/<id>/disband` ends the team (every member is told; they keep working).
- `POST /api/teams/<id>/message` `{"text","from"?}` sends the text to every member but `from` (one removed from the map left out), starting with `[Fleet View · team "<name>"]`, queued behind a menu and resumed when not running, as a message is.

**Menus and answers.** A session that shows a select menu is waiting on you, and a message would answer it by accident, so the API reads it and answers it on purpose.

- `GET /api/sessions/<id>/menu` replies `{"ok","id","menu"}`: `null` when no menu is up, else `{"kind","title","context","options":[{"n","label","desc","on"}],"sig"}`, read from the screen the way the Chat box's question card reads it (`screen.js`, the rows as drawn so a narrow panel's menu is found too). `kind` is `"question"` (an AskUserQuestion), `"permission"` (a tool asking to run, edit or create), `"plan"` (the plan approval), `"trust"` (trust the files in this folder) or `"other"`; `context` is the lines above the title (the command or the diff it asks about), `on` marks the highlighted option, and `sig` changes whenever the menu does.
- `POST /api/sessions/<id>/answer` `{"option","sig"?,"text"?,"allowPermission"?,"wait"?}` picks option `n` (writes its digit), or presses Esc once for `"option": "esc"`. `409` with `"menu": false` when no menu is up, and `409` with `"stale": true` and the current `menu` when `sig` was given and the menu has changed since. Every menu but a `"question"` (a `"permission"` prompt, the folder `"trust"` question, the `"plan"` approval, or one not recognised, `"other"`) needs `"allowPermission": true` to pick an option, else `403`, so a script can never approve a tool call by accident; Esc never needs it. `sig` is 12 hex characters. An option not on the menu is `400`. `text` is for the free answer of a question (an option whose label starts "Type something"): it picks that option, pastes the text (the same rules as a message) and presses Enter. It waits up to 3 s for the menu to change and replies `{"ok","id","answered":{"n","label"} or "esc","next"}`, `next` being the menu now (a question with several tabs shows the next one) or `null`. With `wait` it then waits for the turn like a message does.

**Waiting for the reply.** After every send the call waits (up to 6 s) until Claude has taken the message up, so a status read right after it can't see the `"idle"` from before; `taken` says whether it did (a message queued behind a busy turn is taken up only when that turn ends). With `"wait": true` (up to 30 minutes) or `"wait": <seconds>` (1 to 3600), start, message, answer and open answer only when the turn that message started has ended: `done` is `true`, `endedBy` is `"reply"`, `"question"` (Claude asked something; the question is in `question`), `"menu"` (a select menu came up mid-turn, such as a permission prompt; it is in `menu`, as above, and the screen is checked for one every 2 s), `"apiError"`, `"exit"` or `"gone"`, and `reply` holds Claude's latest reply. When the time runs out, `done` is `false` and `timedOut` is `true`; the session keeps going. Hanging up stops the wait, not the session.

**Cleaning up.** Every session a script starts stays on the map until it is removed. Start throwaway ones with `"temp": true`, or end them with stop `{"remove": true}`, so nobody has to remove stale test conversations by hand.

`prompt` and `text` are at most 64 KB (the server's limit for any request body). `\r\n` counts as a new line; any other control character but new line and tab is refused (`400`), so nothing in the text can end the paste early or press a key. A failed request writes one line to `server.log` (the request and its answer, never the token or the text); a request that works writes nothing.

**`chrome` and the session host.** The flag lives in `desktop/host.js`, and a changed `host.js` takes effect only when the session host restarts: `node desktop\restart-host.js`, or tray **Quit everything** (either saves and ends the sessions, and the next host resumes them). Until then `chromeApplied` says `false` and sessions start with the account's own setting.

**The `fv` command line.** `fv` (`fv.cmd`, and `fv` for Git Bash, at the repo root; `scripts/fv.js` does the work, Node with no dependencies) is the API from a terminal, the easy way for a Claude session to drive other sessions. It reads the token itself; `--port` or `FLEET_VIEW_PORT` picks another server (default 4777). It prints short readable lines; `--json` prints the raw reply. Exit code `0` is ok, `1` refused or failed, `2` bad usage. A text argument of `-` is read from stdin. An id can be its first 8 or more characters, as long as only one conversation starts with them.

| command | |
|---|---|
| `fv api` | the endpoint list (`GET /api`) |
| `fv version` (or `fv --version`) | this folder's Fleet View version, read from `version.json` without the server, and the running server's when it answers |
| `fv ls [--all] [--state S] [--repo R]` | every conversation: id, name, state, repo, the hosted ones marked |
| `fv hosted` | the hosted sessions |
| `fv start <repo> <prompt> [--account A\|B\|C…] [--name N] [--model M] [--effort E] [--fork <id>] [--temp] [--chrome\|--no-chrome] [--wait [s]]` | starts a session (account B unless told) |
| `fv send <id> <text> [--wait [s]] [--from <id>] [--no-open]` | a follow-up; with `--from`, a message from that conversation (queued behind a menu; one not running here is resumed first, unless `--no-open`) |
| `fv wait <id> [--timeout s]` | waits until it is ready for you |
| `fv read <id> [--tail n]` | its status and latest reply |
| `fv menu <id>` | the menu on its screen: title, numbered options with descriptions, kind, sig |
| `fv answer <id> <n\|esc> [--text T] [--sig S] [--allow-permission] [--wait [s]]` | answers it |
| `fv interrupt <id>` | Esc, mid-turn |
| `fv open <id> [--account A\|B\|C…] [--prompt P] [--wait [s]]` | resumes an old conversation |
| `fv transcript <id> [--since n] [--limit m]` | its transcript |
| `fv stop <id> [--remove]` | ends it (and takes it off the map) |
| `fv rm <id>` | takes a conversation off the map |
| `fv teams` | the teams and their members |
| `fv team new <id> <id>… --order T [--name N]` | makes a team of exactly these; each gets the order and its teammates |
| `fv team add <team> <id>` | adds a conversation (it gets the order, the others its id) |
| `fv team rm <team> <id>` | takes one out (it and the others are told) |
| `fv team disband <team>` | ends the team (every member is told) |
| `fv team say <team> <text> [--from <id>]` | a message to every member (but you) |

`<team>` is a team's id, the start of it, or its name, as long as just one team matches.

`--wait` with no number means the API's default. When a wait ends on a question or a menu, `fv` prints it with its options and the exact `fv answer` command to run.

```sh
fv start Z:\Github\fleet-view "List the endpoints api.js serves." --model haiku --temp --wait
fv send 3f2a9c1e "Now the ones that need a running session." --wait
fv menu 3f2a9c1e
fv answer 3f2a9c1e 2 --wait
fv stop 3f2a9c1e --remove
```

**The Claude Code skill.** `skills/fleet-view/SKILL.md` teaches a Claude session when and how to use `fv`: handing independent work to other sessions in parallel, a cheaper model for lookups, testing Fleet View with a real session, answering a child's questions, and cleaning up every session it started. `install.ps1` copies it into every Claude login (`~/.claude/skills/fleet-view`, `~/.claude-<letter>/skills/fleet-view`), and **Update now** refreshes those copies.

**PowerShell helper.** `scripts\FleetView.psm1` wraps all of this: `Start-FleetSession` (with `-Name`, `-Model`, `-Effort`, `-ForkFrom`, `-Temp`), `Send-FleetMessage`, `Get-FleetSession`, `Get-FleetReply`, `Wait-FleetSession`, `Get-FleetMenu`, `Send-FleetAnswer`, `Stop-FleetTurn` (interrupt), `Stop-FleetSession` (`-Remove`), `Remove-FleetConversation`, `Open-FleetSession`, `Get-FleetTranscript`, `Get-FleetConversations` (and `Set-FleetPort` for a server on another port). It reads the token itself, sends UTF-8, and turns the API's errors into plain messages. It only makes local HTTP calls from the PowerShell you run it in, so no window or console opens.

```powershell
Import-Module Z:\Github\fleet-view\scripts\FleetView.psm1
$s = Start-FleetSession -Repo Z:\Github\fleet-view -Account B -Prompt 'Summarise the README in three lines.' -Temp -Wait
$s.reply
(Send-FleetMessage $s.id 'Now make it two lines.' -Wait).reply
Get-FleetSession | Format-Table id, status, state, cwd
Stop-FleetSession $s.id -Remove
```

The same without the helper:

```powershell
$t = Get-Content "$env:LOCALAPPDATA\fleet-view\api-token"
$h = @{ Authorization = "Bearer $t" }
$api = 'http://127.0.0.1:4777/api'

# start a session with a prompt
$body = @{ repo = 'Z:\Github\fleet-view'; account = 'B'; prompt = "Summarise the README in three lines."; wait = $true } | ConvertTo-Json
$s = Invoke-RestMethod -Method Post -Uri "$api/sessions" -Headers $h -ContentType 'application/json' -Body $body
$s.reply

# its status, latest reply and the last 2000 characters of its screen
Invoke-RestMethod -Uri "$api/sessions/$($s.id)?tail=2000" -Headers $h

# a follow-up
$msg = @{ text = 'Now make it two lines.' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$api/sessions/$($s.id)/message" -Headers $h -ContentType 'application/json' -Body $msg

# every hosted session, then stop this one
(Invoke-RestMethod -Uri "$api/sessions" -Headers $h).sessions | Format-Table id, status, state, cwd
Invoke-RestMethod -Method Post -Uri "$api/sessions/$($s.id)/stop" -Headers $h
```

### Opening files and folders

`POST /reveal` opens only what the page was given: a file some conversation touched (`files[].abs`, `calls[].file`), or a repo or checkout folder (`repo.root`, `links.repoFolder`). Any other path gets `403`. A path with `"`, `%`, `^`, `&`, `|`, `<`, `>` or a control character is refused with `400`, since VS Code's `code.cmd` is a batch file and has to run through `cmd.exe`; the path is passed to it in quotes, and to Explorer as a plain argument, never through a shell otherwise. VS Code is looked for at `%LOCALAPPDATA%\Programs\Microsoft VS Code\bin\code.cmd`, then in Program Files, then on `PATH`. Without VS Code the file is shown, selected, in Explorer; it is never handed to its default app, which would run a script or program a session wrote. In `--demo` nothing opens (`{"ok":false}`).

## The live feed mod

`mod/fleet-view-feed` is a Claude Code [mod](https://code.claude.com/docs/en/plugins/mods/overview): code that runs inside each `claude` (2.1.287 or later). On every turn start and end and every tool call it writes `%LOCALAPPDATA%\fleet-view\live\<sessionId>.json` (whether a turn is open, how the last one ended, the tool calls running now and which subagent runs each). Fleet View reads it with Claude Code's own `sessions/<pid>.json`, so it knows a turn is open instead of guessing from the log, and counts it only when the claude running now wrote it. Without the mod everything works as before. `install.ps1` installs it into every Claude login (`~/.claude` and each `~/.claude-<letter>`): the `mod` folder is a plugin marketplace read in place, so a `git pull` updates it for the sessions started after. By hand: `claude plugin marketplace add <fleet-view>\mod`, then `claude plugin install fleet-view-feed@fleet-view`.

## What the cards show

- **Status**: `WORKING` (mid-turn), `AGENTS` (subagents or a workflow running), `NEEDS YOU` (it is waiting on a multiple-choice question, or its live claude says it waits on you: a permission prompt at once, or a panel such as `/usage` left open once the turn is over), `ASKED YOU` (its reply closes on a question), `API ERROR` (stuck until you retry), `STALLED?` (quiet for 5 minutes mid-turn; when its live claude has sat idle meanwhile, it was cut off and the card says to tell it to continue). With the live feed mod (below) a turn its claude still has open stays `WORKING` while a tool runs, however long, and is `STALLED?` only after 15 quiet minutes with none running; the `▸` line then shows how long the running tool has been at it. A conversation that finished its turn without a question leaves the list at once; the alert line names it and the footer counts how many are hidden. In the app window it moves to the "recently finished" strip for 3 hours.
- **goal**: the running workflow's description, or your last message to that session.
- **▸**: the latest tool call in the session or any of its agents, labelled with the agent.
- **Progress bar**: `plan` while a workflow runs (phases passed plus the share of agents done in the current phase), otherwise `ship`, the share of the ship track done. A comet sweeps the unfilled part while the session works. After it, one dot per agent (`●` done, `◉` running, `✕` failed) and the names of the agents running for that conversation.
- **Ship track**: `push → PR → checks → merged → live`, from the session's own `git push` calls and its latest PR on GitHub: check results, merge, and the production deployment. When you message a session, or it pushes or starts a plan, after its PR merged, the track starts again for the new work.
- **Alerts**: a line under the header names the session when it finishes, asks you something, a plan finishes, an agent fails, checks fail, a PR merges, or it goes live. Nothing flashes, blinks or rings: no bell, no taskbar blink, and colours hold steady instead of pulsing.
- **Tokens and cost** (`4.7M tok  $5.91`): every token the conversation and all of its agents used, priced at Anthropic API list prices per model, with cache reads and cache writes at their own rates. It is what the same work would cost on the API, not what a Claude plan bills you. A trailing `…` means its history is still being read; the first start reads all of it in the background, about a minute for 600 MB of logs. The header total covers every conversation seen since Fleet View started, whatever the filter, and counts each message once even when a forked or resumed conversation copied it into its own log.
- **Sparkline**: tool calls per minute over the last 20 minutes. **stream**: every tool call across all sessions, newest first.

- **Colours come in families**: each repo has one base colour, its conversations are close shades of it, and their agents take their conversation's shade, so clusters read at a glance.
- **Conversations** are the hubs, labelled with their title. The halo grows with tool calls in the last 20 minutes. Colours follow the card statuses.
- **Agents** orbit the conversation they work for: `◉` running, `●` done, `✕` failed. With nothing selected (at launch, or after a click on empty space) every agent is labelled; with a selection, only those of the selected conversation.
- **Several repos** each get their own area: the clusters sit on a grid shaped like the window, biggest first, so they use the width instead of piling up in the middle.
- **Zooming** changes how much text shows, since a terminal can't make its font smaller: zoomed out, repo names turn into titles, conversation names shorten, and PR numbers and read-only shared files drop their labels; zoom in and full names come back.
- **Repos** (`◆`) link every conversation working in them, so conversations cluster by repo. A conversation's repo is the git repo its recent file edits and shell paths point at most, with worktrees counted as their main repo.
- **PRs** (`#666`) hang off their conversation, coloured by ship stage: dim (none or stale), cyan (checks passed), gold (checks running), violet (merged), mint (live), red (failed).
- **Shared files** (`⚠ name`) appear only when two or more conversations touched the same file in the window (the same path in different worktrees of one repo counts as the same file). Red means two or more of them edited it, gold means only reads overlap.
- **Sparks** run along an edge on each tool call, as a small comet with a fading tail: agent → conversation for agent calls, conversation → repo for its own.
- **Lines** blend from the conversation's colour to the colour of what they link to.
- **Arrivals and departures**: a new node fades in dot by dot with its lines, and one that leaves (a finished agent, a conversation that ended) dissolves where it was.
- The bottom strip shows the selected node: the full card for a conversation, or the agent's latest call, the repo's conversations, the PR's ship track, or who touched a shared file (`✎` edited).

The layout is a small spring and repulsion simulation. New nodes start next to something they link to and existing ones keep their place, so the map settles instead of jumping, then drifts slightly at rest. Only the rows that changed are written each frame.

It only reads the session logs under `~/.claude/projects` and `~/.claude-a/projects`. It never writes there.


**Recently finished on the map.** Every conversation in the Recently finished strip also shows on the map as a small, dim, steady dot on its repo. Each strip row has a × (on hover or keyboard focus) that removes it, the same as Remove in the right-click menu: it leaves the strip and the map together.

**Repo icons.** A repo is a faceted hexagon in its colour with a ring of six arcs turning once every 20 s; its name sits on a pill right next to it. When a spark arrives, the icon grows to about 1.15x and back (350 ms) and the ring turns an extra 30 degrees. Motion only: nothing gets brighter.

### Map command center

The map also shows how the conversations relate, and lets you steer several at once. Everything here keeps the house rule: steady colours, motion at constant brightness, nothing blinks; with "reduce motion" on, it holds still.

- **Teams** are drawn as a soft braided double line in the team's colour between its members, with a small pill bearing the team's name at the middle; hovering it shows the order and the last messages. A message between two conversations sends a comet along that line, and a new order sends one from the pill to each member. Right-click the line or pill for the team's menu.
- **Conflicts** are nodes like shared files, with springs to the conversations involved: a branch sign for two on the same branch, a folder for two in the same worktree folder, `#nnnn` for two migrations with the same number. Gold for a branch, red for a worktree or migration. The tooltip explains it and says "right-click: actions" (a note to all of them, open the file, pick or interrupt each one).
- **Web and app together** (repos with a parity rule, see **Parity**): a thin dotted line, cyan on the web side and mint on the app side, joins a web conversation and its app partner ("web ↔ app" on hover). A conversation that changed one side only and has no partner gets a small hollow ghost orb beside it with a dashed link, labelled "no app change" or "no web change".
- **Ship** includes the phone app: a PR node and its tooltip show the `app` step (update, build or submit, and for which platforms), and its colour counts it.
- **Handoff trails**: a faint line with a small arrow from the conversation a handoff was picked up from to the one that took it over (finished ones included while they are on the map), and a tick on a conversation's memory gauge at its handoff size.
- **Worktrees** are tiny satellites on an outer ring around their repo's hub: filled while a conversation works in one, hollow and dim when it is stale (no live conversation and no commit for 3 days). Hover one for its name, branch and last commit; the hub's tooltip lists the stale ones.
- **Lenses** (`k`, or the small segmented control at the top left): **State** (the usual colours), **Cost** (orb size and colour by cost), **Account** (A and B colours), **Idle** (fresh activity cyan, fading with time since the last one), **Context** (by how full the context window is). Saved as `mapLens`.
- **Saved views**: `Shift`+`1`–`9` saves where you are (pan and zoom), `1`–`9` glides back (saved as `mapViews`).
- **Needs you**: `n` / `N` glide to the next / previous conversation that needs you. One that needs you and is off screen gets a small chevron at the edge of the map pointing at it, with its name and how long it has waited ("asking · 12m"); a click on it glides there and picks it. Pointers that would overlap stack ("+2").
- **Minimap**: zoomed in (or with a map larger than the window), a small map at the bottom right shows every node and the part in view; click or drag on it to move there.
- **Replay** (`t`, or the clock button at the bottom left): a bar along the bottom with a 1h / 6h / 24h range, a slider, play and pause at 1x, 10x or 60x, and **Live**. The map then shows how things stood at that moment (from `GET /timeline`: who was working, waiting or done, their repos and costs, and the tool calls as comets), and the header shows "Replay · 10:42 PM"; a click on that pill, **Live** or `Esc` goes back to now. Only the map replays: the other views and the header counts stay live.
